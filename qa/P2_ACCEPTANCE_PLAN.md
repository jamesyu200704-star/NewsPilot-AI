# P2 端到端人工验收计划

## 前置条件

- 使用无个人信息的浏览器配置；公开 Demo 保持 Mock。
- 每轮开始前导出已有本地项目备份。
- 导入 `fixtures/` 中对应项目，确认页面明确保留“虚构任务”语义。
- 记录浏览器、视口、版本、测试人和时间。自动化脚本不得冒充人工验收。

## 场景一：人物特稿

依次完成：作业要求解析 → 人物特稿项目 → 主角与旁证 → 采访计划 → 采访笔记 → TXT/Markdown 逐字稿 → 人工确认直接引语 → 人物时间线 → 报道结构 → 作业自查 → DOCX。

重点观察：主角和旁证是否分开；大纲是否有场景、变化和旁证；引语能否追溯；未确认引语是否被阻断；人物故事硬要求是否进入自查。

## 场景二：校园现象调查

依次完成：输入现象 → 区分事实/传闻/假设 → 多方信源 → 文件与公开资料 → 学生/教师/管理者采访 → 保留不同观点 → 更新证据矩阵 → 补缺口 → 调查型大纲 → 证据表。

重点观察：社交媒体仅作线索；转载去重；冲突不被抹平；用户假设不升级成事实；替代信源现实可达。

## 场景三：校园政策观察

依次完成：输入线索 → 找政策原文 → 核对日期/范围 → 采访执行者与受影响者 → 识别执行差异 → 保留冲突 → 政策观察大纲 → 课程自查 → Word。

重点观察：旧政策不冒充现行政策；学校规定与课程要求分开；文件规定和实际执行分开；系统不擅自裁决冲突。

## 证据要求

每个 `passed` 项至少有一条实际结果；视觉项需要脱敏截图；导出项需要文件打开记录。任何数据丢失、隐私泄露、虚构引语、off the record 误导出或关键假核实均记为 Critical 并停止发布。
